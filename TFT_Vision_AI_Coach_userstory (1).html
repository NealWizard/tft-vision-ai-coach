研发原则

开发顺序
先确定性、后概率；先数据、后视觉；先状态、后决策；先离线、后在线；先记录、后学习；先单体模块、后 Orchestrator。
硬边界
纯视觉/截图/视频/摄像头输入；不读取游戏进程内存、不注入、不 Hook、不拦截游戏网络、不修改客户端、不模拟键鼠、不自动执行游戏操作。
Live
Live Experiment、Live Dynamic Recommendation、Live Opponent Analysis 默认关闭；是否推进由当前第三方政策/产品注册/官方确认决定。
计划时间
下面日期均为“计划开始/计划完成”而非已完成时间。实际完成时间需要研发推进后回填。

任务清单

任务列表采用响应式卡片布局，避免原先 16 列宽表在预览窗口中出现横向裁切。需求、验收、依赖、计划、状态、实际完成时间与负责人均完整显示。

阶段门禁

V0.1：数据模型、CI、安全边界稳定。
V0.2：Knowledge 查询可复现、Evidence 完整、Patch 隔离。
V0.3：OCR/GameState 达到基线并可重建 Timeline。
V0.5：Domain Agent 可离线评测，统一 Candidate Set。
V0.8：Replay + Feedback + Player Profile 闭环。
V0.9：Orchestrator 可端到端调用。
V1.0：离线/赛后/赛前能力完整、可部署、可回归；Live 默认关闭。

建议的需求管理落地方式

这份 HTML 适合作为当前项目的“单一规划快照”和评审入口。正式研发时，建议将每一行映射成 GitHub Issue，并以 P0/P1/P2 作为优先级、Phase 作为 Milestone、Domain 作为 Label、ID 作为业务编号。这样代码、PR、CI、Issue、讨论天然串联，不需要为了项目管理再维护一套孤立系统。

仓库：github.com/NealWizard/tft-vision-ai-coach。后续可通过 GitHub Issues API 批量创建任务，也可迁移到 Jira、Linear、Plane 等工具。
